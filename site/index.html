Why it exists

"Clean data" usually means nobody counted what was thrown away.

Without it

Raw files are loaded straight into a reporting model. Re-delivered rows double the revenue, a typo in a key silently drops a sale from every join, and nobody can say how many records were lost between source and dashboard.

With it

Bronze keeps the source as delivered. Silver types, deduplicates and moves every invalid row to a reject table with its reason, so Bronze always equals Silver plus rejects. Gold is a star schema in which every fact key is checked against its dimension.

How it works

Three layers, each with one job

01

Seeded, honest test data

The generator is reproducible with --seed and can inject duplicates, bad amounts, unknown keys and broken timestamps on purpose with --dirty-rate.

02

Bronze: as delivered

Every column kept as text, with ingestion time and source file, so Silver and Gold can always be rebuilt.

03

Silver: typed and judged

Exact re-deliveries removed, invalid rows rejected with a reason, suspicious rows flagged for review instead of silently dropped.

04

Gold: star schema and reports

fact_transaction with player, game, location and date dimensions, plus daily_sales, game_performance and player_activity.

Run it yourself

Run it locally

Python 3.12+. Open local/lottery.duckdb in any DuckDB client to query the bronze, silver and gold schemas.

git clone https://github.com/phlppgdfry/fabric-lottery-data-platform
cd fabric-lottery-data-platform
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

python data-generator/generate_data.py --dirty-rate 0.01
python local/pipeline.py --db local/lottery.duckdb --summary local/summary.json
pytest -q tests
